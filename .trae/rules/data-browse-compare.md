# 从 JSON 数据构建浏览 + 对比页面

## 这个 skill 解决什么问题

用户手上有一份 JSON（或可转成 JSON 的数据），里面是几十到几千条“同类实体”的记录，字段覆盖率参差不齐。用户想要一个页面：能浏览全部记录（搜索、筛选、排序、分页），能点击单条查看详情，能勾选几条记录并排对比差异。

典型场景：云服务定价表、商品/SKU 清单、API 模型规格、招聘岗位列表、竞品功能矩阵——任何“N 条记录 × M 个字段，字段有缺失，用户想挑几条细看差异”的数据。

## 何时应用本规则

除了「从零生成页面」，**凡是涉及让页面数据变新的诉求，都要应用本规则**——重建页面的入口就是 `scripts/build.py`，它默认会先拉取上游最新数据再重建。以下说法（及同义表达）都属于触发范围：

- 「更新数据」「更新一下数据」「数据更新了」
- 「更新模型数据」「模型有新增/变动，更新一下」
- 「重新拉取模型数据」「拉取最新数据」「拉一下上游最新 JSON」
- 「刷新数据」「同步上游数据」「同步最新价格/模型」
- 「重新生成页面」「重新构建 index.html」「重新跑一下 build」「跑 build.py」
- 「上游数据变了，重新出一份页面」

这类诉求的处理方式：直接运行 `python .claude/skills/data-browse-compare/scripts/build.py`（它会拉取最新 JSON → 重建 index.html → 记录 diff，全流程原子化），不要手工编辑 index.html 里的数据块，也不要只更新 source-data/ 下的 JSON 而不重建页面（那样页面展示的仍是旧数据）。

只想用本地已有 JSON 重建、不拉取远程时（离线/调试），才加 `--no-fetch`。

## 核心方案：零依赖单文件静态页面

除非用户明确要求用某个框架，默认用**纯 HTML + 原生 JS + 内联 CSS**。

理由：
- 数据是静态的，不需要后端。
- 单文件双击即可打开，零门槛使用、分享。
- 避免构建工具链复杂度，几千条记录的规模客户端完全够用。

如果用户主动提到 React/Vue 或需要更复杂交互，才转向对应技术栈；不要主动建议升级架构。

## 视觉主题：白底 + 冷色 accent 的「实验室控制台」

这类数据工具页面默认走**科技感、高级感、简洁直观**的方向，白色背景。推荐配色与手法：

- **主色用冷色**，不要用暖色。深青蓝（如 `#0e7490` petrol/teal）一档最稳——冷色天然契合"数据/云/技术"，白底上高级不刺眼。暖金、橙色系更偏"奢华/消费"，与数据工具气质不符。
- **展示字体用几何无衬线**（如 Space Grotesk），不要衬线；中文回退 Noto Sans SC；数字/代码列保留等宽字体（JetBrains Mono）——等宽数字是数据表格的正确选择。
- **白底不等于一片平白**，用这些手法做层次：
  - hero 区铺浅 accent tint 的垂直渐变 + 一角径向光晕 + 细网格纹理（约 56px 的工程图纸格线，向下渐隐 mask），立刻有"控制台面板"的纵深感。
  - 面板/分组标题用浅 accent tint 底色（而非中性灰），呼应主题。
  - 主按钮带 accent 色光晕阴影，hover 加深——白底上迅速立体。
- **辅助色系统一冷化**：边框、灰阶文字、hover 底色都往冷灰调，不要残留暖灰/暖白；强调绿（最优值）选与主色同色相家族的绿（如 `#0d9463`）。

## 多语言（i18n）：轻量字典 + data-i18n，默认英文

这类工具天然适合做中英文切换——**数据层（key/provider/mode）通常全是英文 slug 无需翻译**，只需覆盖 UI 层文本。不要引入 i18n 框架，用轻量字典即可：

- **核心结构**：一个 `I18N = { zh: {...}, en: {...} }` 字典（两语言 key 必须完全一致），`t(key)` 取动态文本、`L(obj)` 取 `{zh,en}` 映射值（用于 MODE_LABELS / 能力分组这类数据驱动的文案）。动态文案（如"共 X 个模型"）在字典里存成函数 `statsText: (f,total,sel) => ...`。
- **静态文本**：HTML 元素加 `data-i18n="key"`，placeholder/title 分别用 `data-i18n-ph` / `data-i18n-title`，切换时 `applyI18n()` 遍历替换。
- **数据驱动的映射表**（如 mode 中文名、能力标签）：值从纯字符串改成 `{ zh: '...', en: '...' }`，渲染处统一用 `L()` 按当前语言取值。
- **切换器**：hero 右上角放 `中 / EN` 分段按钮，选择存 `localStorage` 持久化；`setLang()` 统一切换 `<html lang>`、`<title>`、切换器高亮，然后重渲染所有视图。
- **默认英文**：面向技术用户的工具建议默认英文（`localStorage.getItem('lang') || 'en'`），并把静态 HTML 的初始文本直接写成英文，避免首屏"先中文后英文"的闪烁。可写个脚本把 `data-i18n` 元素的初始文本批量替换成 en 字典值，保证一致。

**两个易漏的点**：
- **JS 动态填充的控件**（如对比页的 provider/模型下拉）不会随 `applyI18n()` 更新——切换语言后要调用对应的重建函数刷新（含"其他/Other"这类兜底项、placeholder、"无匹配结果"文案）。
- **title 悬停提示**里的中文也要一并翻译（`data-i18n-title`），别只翻可见文本。

## 典型页面结构

一个完整的页面通常由以下区块组成，按使用流程自然铺开：

1. **Hero / 页头**：一句话说明页面用途，并展示关键汇总指标（条目总数、分类数、Provider 数等），让用户一眼感知数据规模。
2. **Tab 导航**：「浏览全部」与「对比」两个标签页。对比页在勾选为空时显示友好提示。
3. **浏览视图**：搜索、筛选、排序、分页表格，每行带勾选框。
4. **详情抽屉**：点击表格行（除勾选框外）打开侧滑抽屉，展示单条记录完整信息，并可在抽屉内将其加入对比。
5. **对比视图**：并排展示已选记录，按维度分组，自动高亮唯一最优值。
6. **已选产品弹窗**：勾选 ≥1 条记录时在浏览页底部弹出卡片式弹窗，标题栏显示”已选择 N 个”，右上角有很小的 ✕ 用于一键清除，下方显示已选项 chip 和”开始对比”按钮。**只在「浏览全部」tab 下显示**，「对比」tab 下不显示（对比页本身就是目的地）。

## 图标系统：用内联 SVG sprite，不要用 emoji

**不要用 emoji 当图标**——emoji 在不同平台渲染风格完全不同（Windows/Mac/iOS 各画各的），自带彩色填充与精致配色冲突，大小基线不一，且部分语义牵强（如 🔺=最大推理强度、🌊=原生流式）必须靠 title 才能看懂，整体显得廉价。

改用**手工设计的内联 SVG 图标系统**：
- 在 body 开头放一个隐藏的 `<svg>` sprite，里面用 `<symbol id=”i-xxx”>` 定义全部图标，各处以 `<svg class=”ic”><use href=”#i-xxx”/></svg>` 引用。
- 统一规格：`viewBox=”0 0 24 24”`、`fill=”none”`、`stroke=”currentColor”`、`stroke-width=”1.8”`、`stroke-linecap=”round”`，线性几何风格（参考 Lucide/Phosphor 但手工绘制以匹配项目美学）。`currentColor` 让图标继承父元素文字色，配合 `.ic { width: 1em; height: 1em; }` 随字号缩放。
- 用 JS `ic(id)` helper 生成引用串，数据驱动的图标（能力、模态）把映射表里的 emoji 换成 icon id。
- 顺带把 Unicode 符号也换掉：排序箭头 `▲▼`、下拉 `⌄`、关闭 `✕`、外链 `↗`、模态箭头 `→` 全部改 SVG，跨平台渲染才一致。
- 图标数量按需定制（本项目约 45 个：统计、能力矩阵、模态、分组标题、控件各若干）。中文 label 不要套 `text-transform: uppercase` 和宽 `letter-spacing`（那是英文排版习惯，对中文无意义且局促），用字重和颜色区分层级。

## 工作流程

### 第一步：分析数据结构

在写页面代码之前，先用 `scripts/analyze_json.py` 快速摸底：

```bash
python scripts/analyze_json.py <path-to-json>
```

它会输出：条目总数、每个字段的覆盖率、字段值类型分布、数值字段范围、布尔字段 True 占比、数组/对象字段示例。

**另外，如果数据里有 `sample_spec` / `schema` 这类「字段说明」样例对象，务必逐字段对照它检查你的渲染覆盖**——它列出了数据可能出现的全部字段，是发现「字段存在但没渲染」的最直接依据。把它和预处理白名单对比，凡是在 spec 里、却没进渲染管线的字段，就是漏渲染的候选（再按覆盖率决定要不要补）。

**但 spec 不是全集——还要反方向扫一遍「数据里有、spec 里没有」的字段**。spec 是人工维护的说明，常滞后于真实数据（本项目的 `supported_endpoints` 就不在 spec 里，却在 19% 的记录里真实存在）。做法：遍历全部记录收集字段并集，减去 spec 字段和已渲染字段，剩下的逐个看覆盖率和取值形态决定是否补渲染。两个方向都扫过，才算覆盖检查闭环。

带着这些问题读报告：
- 哪些字段覆盖率 >80%？→ 浏览表格核心列。
- 哪些字段覆盖率 <20%？→ 不适合常驻列，可能只在对比视图展开或忽略。
- 数值字段量级如何？→ 是否需要单位换算（如美元/token → 美元/百万 token）、大数字缩写（K/M）。
- 布尔字段是否成组（如大量 `supports_*`）？→ 能力矩阵，适合分组展示或筛选开关。
- 是否有数组/对象字段？→ 需要特殊渲染（join、子行、图标、分组）。
- key 命名是否有规律？→ 判断是否存在“同一实体多个变体 key”。**特别注意：key 里是否带区分同名的前缀**（region、区域、规格、路径段），如 bedrock 的 `us.`/`eu.` region 前缀（`.` 分隔，不在 `/` 路径里）、azure 的 `eu/`/`global/`、openai 的 `hd/`/`1024-x-1024/` 规格前缀——这决定列表展示时能否只取最后一段（见下文「对比页内添加记录」的 key 展示处理）。

如果对“哪些字段该展示、能力矩阵怎么定义、要不要做单位换算”没有把握，用 AskUserQuestion 列出选项跟用户确认，不要自己假设。

### 第二步：数据预处理

在 JS 中加载原始 JSON 后，先做一次规范化转换，不要让模板里到处写字段名回退逻辑。

建议统一做的事：
- **字段映射与回退**：原始数据里同一个概念可能有多个字段（如上下文长度可能是 `max_input_tokens` 或 `max_tokens`），在预处理阶段就确定最终字段。
- **单位换算**：价格类字段如果原始单位是“每 token”，换算成“每百万 tokens”；大数字 token 数换算成 K/M。
- **布尔能力扁平化**：把所有 `supports_*` 字段收集到一个 `caps` 对象中，方便后续筛选和对比视图使用。
- **模态/标签数组**：把 `supported_modalities`、`tags` 这类数组字段保留为数组，供图标或标签渲染。
- **路径/端点类数组**（如 `supported_endpoints`）：同样保留为数组，但展示位置与模态不同——覆盖率低（<30%）且值是长文本路径时不进浏览表格（会撑爆列宽），只在详情抽屉加独立区块、对比视图加一行；渲染用**等宽字体 tag**（路径是代码性质文本），遵循「该记录有才渲染」原则。判断某数组字段是否值得展示时，先验证它相对已有字段是否有增量信息——例如端点不能从 mode 推导（同一 mode 下可能有 10 种端点组合：是否支持 `/v1/responses`、`/v1/batch` 是选型决策因素），这种就该展示。
- **排除非记录项**：如果顶层 dict 里混有 schema 说明（如 `sample_spec`）、元数据，提前过滤掉。

示例（抽象模式，非具体字段）：

```js
const models = [];
for (const [key, raw] of Object.entries(data)) {
  if (key === 'sample_spec' || !raw || typeof raw !== 'object') continue;
  models.push({
    key,
    provider: raw.provider || '',
    mode: raw.mode || '',
    inputPrice: raw.input_cost_per_token != null ? raw.input_cost_per_token * 1e6 : null,
    outputPrice: raw.output_cost_per_token != null ? raw.output_cost_per_token * 1e6 : null,
    cacheRead: (raw.cache_read_input_token_cost ?? raw.input_cost_per_token_cache_hit) != null
      ? (raw.cache_read_input_token_cost ?? raw.input_cost_per_token_cache_hit) * 1e6 : null,
    maxInput: raw.max_input_tokens ?? raw.max_tokens ?? null,
    maxOutput: raw.max_output_tokens ?? null,
    caps: Object.fromEntries(CAPS.map(([f]) => [f, raw[f] === true])),
    inputModalities: Array.isArray(raw.supported_modalities) ? raw.supported_modalities : null,
    outputModalities: Array.isArray(raw.supported_output_modalities) ? raw.supported_output_modalities : null,
    raw,
  });
}
```

**注意白名单陷阱**：上面这种「只拷贝已知字段」的预处理很干净，但代价是**原始数据里新增/长尾的字段会被静默丢弃**——即使保留了 `raw`，如果详情/对比渲染也只读预处理后的命名字段，那些字段就永远不会出现。对策：
- 预处理时把「主干之外的额外字段」也归集成一个数组（如 `extraPrices: extractExtra(m)`），每项存 `{ label, value, unit }` 且**只收录有真实值的**（跳过 null/0），渲染层只遍历这个数组。
- **单位各异的字段在预处理阶段就换算/格式化好**（如 `per_token` ×1e6、`per_session`/`per_query`/`per_GB` 保留原单位），渲染层只负责展示，不写换算逻辑。
- **嵌套对象字段**（如按档位分档的 `{ high: x, low: y }`）在预处理阶段展开成可读字符串。
- 详情/对比里这类额外字段遵循「该记录有才渲染」——没有的记录整个区块不出现，不产生占位噪音。

**专项价格白名单要按「价格档体系」成组覆盖，不要只收零散字段。** 云厂商的定价普遍分档：标准档之外还有 Priority（加价提速）、Batch（批处理半价）、Flex（灵活档，介于两者之间），缓存也分**读/写**两个价格（如 Anthropic 的 `cache_read_input_token_cost` / `cache_creation_input_token_cost`）。只展示标准价会误导选型——一个标准价偏高的模型可能 Batch 档反而最便宜。收集时按后缀族排查：`*_priority`、`*_batches`、`*_flex`、`cache_creation_*` 各自成对（input/output）纳入白名单，单位与主干一致（per_token ×1e6）。注意区分「档位价格」（值得展示）与「阶梯阈值价格」（`*_above_128k/200k/…` 等按用量分段，用「阶梯」标签概括即可，逐一展示会噪声爆炸）。

### 第三步：设计浏览表格

浏览表格是默认视图，展示全部记录，用户从这里挑出要对比的对象。

**必备交互：**
- 顶部搜索框（模糊匹配名称、Provider 等关键字段）。
- 按主要分类字段筛选（下拉选择）。**选项排序按字段基数区分**：基数大的字段（如 provider，上百个选项）按**字母升序**更好找——频次序在大列表里毫无规律可循；基数小的字段（如类型，十几种）按**出现频次降序**更高频优先。字母排序要**统一转小写再比较**（`a.toLowerCase().localeCompare(b.toLowerCase())`），否则大写排在小写前（`Z` 在 `a` 前），顺序反直觉。同一字段的排序口径在浏览下拉、对比页添加下拉、表格列排序里要保持一致。
- 如果数据包含输入/输出模态数组（如 `supported_modalities`），提供输入模态、输出模态的多选 chip 筛选，选中多个时采用“必须同时包含”的 AND 逻辑。
- **能力筛选 chip 用通用委托设计，新增 chip 零 JS 改动**：事件绑定挂 `document.querySelectorAll('.cap-filter input')` 统一处理、筛选逻辑遍历 `state.capFilters` 集合做 AND 判断、能力状态在预处理时由 CAPS 列表自动生成——所以新增一个能力筛选（如"联网搜索" `supports_web_search`）只需加一处 chip HTML（`data-cap="字段名"`）+ 两条 i18n 字典，不要为每个 chip 写专属事件或筛选分支。加之前先查字段覆盖率：True 占比只有个位数百分比时 chip 仍有价值（帮用户精确圈出少数派），但要在心里明确它是"窄筛"而非"常用筛"。
- 表头点击排序（数值列按数值排，文本列按字母排且同样转小写，**缺失值永远排最后**）。
- 分页（超过 100~200 条时必须分页，不要用虚拟滚动）。
- 每行一个勾选框，用于选中要对比的记录。
- **点击行打开详情抽屉**（勾选框点击不触发抽屉）。

**格式化细节：**
- 价格类数值：换算成人类好读的单位，不要直接把 `0.0000025` 糊给用户。
- 大数字：格式化成 `128K`、`1.5M`。
- 布尔值：视觉上要一眼区分开关，不要用纯文字 true/false。
- 模式/类型标签：如果原始值是英文缩写，准备一份 `MODE_LABELS` 映射成中文。
- 用图标增强可读性：在 Hero 统计标签、能力筛选 chip、详情抽屉分组标题、对比视图分组标题等关键位置加图标，能显著提升扫视效率。**不要用 emoji 充当图标**，用一套内联 SVG 图标系统（见下文「图标系统」）。

**能力/模态列的处理**：
- 浏览表格不要把所有 `supports_*` 布尔字段都列成图标——太挤太吵。
- 如果数据有 `supported_modalities` / `supported_output_modalities` 这类数组字段，用它渲染成图标列更清晰。
- 完整的能力矩阵放到对比视图里展开。

### 第四步：设计详情抽屉

点击表格行打开的侧滑抽屉，是“单条记录深度查看”的入口。规则与对比卡片一致：

- **该对象没有的字段/区块整个不渲染**，而不是显示占位符。
- **核心数字优先**：如果价格是最关键信息，用更大字号放在抽屉顶部。
- **分组展示**：价格、上下文、基本信息、支持模态、能力等按区块分隔。
- **加入对比入口**：抽屉底部提供按钮，可直接把当前对象加入对比（共享同一套上限检查逻辑）。
- **关闭方式**：点击遮罩、点击关闭按钮、按 `Esc` 键都应关闭抽屉。

### 第五步：设计对比视图

对比视图不是“表格转置”这么简单。推荐用 **Grid 布局**一次性渲染每一行在所有列上的单元格，这样同一行高度天然对齐，不需要 JS 测高。

**布局与渲染原则：**
- **表头行**：每列展示对象名称、Provider、类型，以及移除按钮。
- **分组标题行**：把字段按语义分组（价格、上下文、基本信息、支持模态、能力），每组一个醒目标题。
- **只比较、不列举全集**：
  - 某个指标在所有已选对象中都是空值，直接不渲染该行。
  - 能力/标签类字段，每张卡片**只展示该对象自己命中的**，不要展示“其他对象有但这个没有”的灰色占位。
- **高亮最优值，但要处理并列**：
  - 数值维度可给“最优”打标（价格越低越好，容量越大越好）。
  - 必须明确“越低越好”还是“越高越好”，不要凭字段名瞎猜。
  - 当多个对象取值相同并列最优时，**不要高亮任何一个**（避免误导）。实现上可先算出一个“最优值下标集合”，仅当集合大小为 1 时才渲染高亮和“最优”标签。
  - 只选了 1 个对象时不需要任何“最优”标记。

**能力矩阵分组**：
如果数据里有大量 `supports_*` 布尔字段，不要平铺成一个标签墙。按语义分组（例如输入类型、工具与函数调用、推理能力、输出与结构化、系统与会话、其他），每组独占一行，方便扫视比较。

**记录 key 的展示**：列表/下拉里展示记录时，key 常带区分同名的前缀（region、区域、规格、路径段）。**不要只显示最后一段**——bedrock 的 region（`us.`/`eu.`，`.` 分隔）、azure 的区域（`eu/`、`global/`）、openai 的规格（`hd/`）、fireworks 的路径（`accounts/…/models/`）等前缀才是区分同名变体的关键，去掉就会撞名。推荐主名显示最后一段、前缀以小字附后（如 `gpt-4o · azure/eu/`），完整 key 放 `title` 悬停可见。先做数据核查（统计同一分类下去前缀后的撞名率）再决定展示策略，别只给某个 provider 特判。

### 第六步：设计入口交互（勾选 → 对比）

从“浏览”到“对比”的路径要顺畅：
- 勾选达到上限（如 3 个）时，用 toast 提示并自动跳转到对比视图。
- 勾选 1 个以上但未到上限时，浏览页底部弹出”已选产品”卡片弹窗：标题栏显示”已选择 N 个”，右上角提供很小的 ✕ 按钮，点击后清除所有已选产品；弹窗内显示已选项 chip（可单独移除）和”开始对比”按钮。
- 所有计数显示（Tab 徽标、对比工具栏文本、席位指示点、已选产品弹窗）用同一个函数统一刷新，避免不一致。
- 对比页为空时，提示文案里的「浏览全部」应做成可点击链接，一键切回浏览标签继续勾选。
- 对比视图内每列提供移除按钮，移除后同步刷新浏览视图的勾选框状态。
- **刷新后保持现场**：把「当前 tab + 已选记录 key 数组」持久化到 `localStorage`，启动时恢复——用户选好 3 条进入对比后刷新，应完整还原对比页而不是回到空白浏览页。恢复时校验已选 key 是否仍存在于当前数据（剔除已下线的），已选为空时不恢复对比 tab（恢复一个空对比页没有意义）。计数徽标的刷新要挂在 tab 切换的统一入口里，否则「刷新恢复到对比页」这条路会漏刷徽标显示 0。
- **对比页内可直接添加记录**：在对比工具栏放「先选分类（Provider）→ 再在该分类下搜索记录」的两级联动选择器，让用户不从浏览页来回切就能补齐对比席位。分类下拉按记录数降序；记录下拉用「输入框 + 悬浮多行 select」实现（`mousedown` 抢在 `blur` 前读取选中值），选中后该选项置禁用，席位未满可连选，选满即禁用两个控件。禁用态挂在统一计数刷新函数上，并保证工具栏 `z-index` 高于下方对比表（对比表的粘性表头/相对定位单元格会遮挡下拉）。**注意：选中后必须同时重渲染对比表格**——如果添加逻辑复用的选中函数只刷新浏览表格，在对比 tab 下选中的记录就只进了 state、不更新视图，用户得刷新页面才能看到（见「常见坑」）。

### 第七步：把数据内嵌进最终交付的那一个文件

浏览器 `file://` 协议禁止 `fetch()` 读取本地文件，所以最终交付的 `index.html` 必须自包含数据。

**页面模板独立成文件，build.py 从模板 + 数据全量重建页面。** skill 目录下有一份 `template.html`（完整页面代码，数据块位置用 `<!--MODEL_DATA-->` 占位），`scripts/build.py` 读它 + 新 JSON 拼出整个 `index.html`。这样**数据或模板任一变化都能从零重建**，而不是只能在已有页面上换数据。

模板里的加载逻辑写成“优先读内嵌数据、没有则退回 fetch”，因此 `template.html` 本身可直接用 `python -m http.server` 开发预览（占位注释走 fetch 分支）：

```js
async function loadData() {
  let data;
  const embedded = document.getElementById('model-data');
  if (embedded) {
    data = JSON.parse(embedded.textContent);
  } else {
    const resp = await fetch('source-data/xxx.json');
    data = await resp.json();
  }
  return data;
}
```

**生成流程是原子的**，避免中途失败留下损坏的 index.html——先生成中间产物、验证通过才替换正式文件：

```bash
python .claude/skills/data-browse-compare/scripts/build.py
```

0. **前置拉取**：默认先从上游拉取最新 JSON 到临时文件并校验（`--no-fetch` 跳过、改用本地；显式 `--data` 也会跳过）。**本地 JSON 在最后一步才替换**——任何前置失败，本地数据和页面都保持旧版不被污染；
1. 模板 + 数据拼出 `index-new.html`；
2. 验证：数据块能被 `JSON.parse` 解析、条目数与源数据一致、页面 JS 通过 `node --check` 语法校验（无 node 则跳过并提示）；
3. 验证通过：把现有 `index.html` 改名为 `index-old.html`（备份），再把 `index-new.html` 改名为 `index.html`，最后才把拉取的新数据写回本地 JSON；
4. **后置 diff**：对比拉取前后的新旧数据，把**新增 / 减少 / 变更**的模型简洁信息（key + provider/mode + 价格）追加写入 `diff/<YYYY-MM-DD>.txt`——同一天多次执行追加不覆盖，仅在拉取模式且有旧数据可对比时生成；
5. 任一步失败：保留原 `index.html` 和本地 JSON 不动，删除临时文件，非零退出。

注意：条目数统计要排除 `sample_spec` 这类 schema 说明项——它是字段示例不是真实记录，不计入（也不应计入页面展示的模型总数）。

数据量较大时内嵌后文件会变大，这是预期正常现象，跟用户说明一下即可。

## 常见坑

- **`<td>` 不要直接设 `display: flex`**——要在 `<td>` 内部再包一层 `inline-flex` 容器，`<td>` 本身保持 `table-cell`，并统一设 `vertical-align: middle`。
- **不要用 emoji 当图标**——跨平台渲染不一致、自带彩色与配色冲突、基线参差，用内联 SVG sprite 替代（见上文「图标系统」）。
- **悬浮下拉会被下方表格的表头/定位单元格遮挡**——对比表用了 `position: sticky` 表头或 `position: relative` 单元格时，要确保承载下拉的容器 `z-index` 高于表格容器，否则下拉会被盖住点不到。
- **固定定位的弹窗会遮挡页面底部控件**——用 JS 动态给被遮挡容器加 `padding-bottom`，已选产品弹窗出现时留出空间、消失时收回。
- **浮层显隐的判断要收拢在渲染函数里**——比如「已选产品弹窗只在浏览 tab 显示」，应让渲染函数自己判断当前 tab，而不是依赖各调用方按正确顺序处理，否则刷新恢复、自动跳转等路径会漏处理导致弹窗在错误的 tab 下闪现。
- **多 tab 下，状态变更要刷新所有受影响视图**——比如「选中记录」这个状态同时驱动浏览表格（勾选框）、对比表格、计数徽标、弹窗。若选中函数只刷新浏览表格，那么在对比 tab 内通过下拉添加记录时，对比表格不会重渲染，用户看到的还是旧数据、以为没选中。修法：选中函数里按当前 tab 补一句 `if (state.tab === 'compare') renderCompare()`；同理「选满自动跳对比」这类副作用也应判断 `state.tab !== 'compare'` 再触发，避免在对比页原地跳转。
- **`size>1` 的 `<select>` 才能自定义 option 的 hover 样式**——`size=1` 的弹出式下拉由操作系统绘制，CSS 改不动；`size>=2` 的列表框由浏览器渲染，写了自定义 `background`/`color` 后 `:hover` 高亮就生效。悬浮下拉里若 hover 无反馈，先确认用的是多行 select 而不是单行下拉。
- **不要用 `alert()`/`confirm()` 做提示**——用 toast（定时消失的浮层提示）代替。
- **排序时缺失值不要排在最前**——`null`/`undefined` 在升序和降序时都排最后。
- **内嵌数据到 `<script>` 标签时转义 `</`**——用 `.replace('</', '<\\/')` 处理。
- **页面生成要做成原子替换**——先产出中间文件（index-new.html）、验证通过再转正并把旧版备份为 index-old.html；不要边写边覆盖正式 index.html，否则中途失败会留下损坏的页面。
- **表格行点击与勾选框点击要隔离**——勾选框 change 事件不要冒泡触发抽屉打开。
- **并列最优不要高亮**——多个对象取值相同并列第一时，不要只高亮其中一个，应视为同等优秀。
- **抽屉/弹窗要提供多种关闭方式**——关闭按钮、点击遮罩、按 `Esc` 都应能关闭。

## 验证方式

1. **数据完整性**：用 Python 读原始 JSON，统计条目数、关键字段值，跟页面搜索/筛选结果做数值比对。
2. **内嵌结果验证**：`build.py` 跑完后，检查 `index.html` 里的数据块能被 `JSON.parse` 正常解析、条目数对得上、JS 语法没问题（可用 Node 的 `new Function(jsCode)` 快速验证）。
3. **交互逻辑验证**：可用轻量 Node.js 脚本模拟 DOM 桩，测试勾选、计数、已选产品弹窗、对比视图切换、抽屉打开/关闭等状态联动。
4. **i18n 完整性**：两语言字典的 key 集合必须完全一致。可用 Node 实际 eval 出 `I18N` 对象，比对 `Object.keys(zh)` 与 `Object.keys(en)` 的差集（应都为空），再对照代码里所有 `t('...')` / `data-i18n` 引用确认无缺失——比肉眼比对可靠。注意剔除 `t('option')`、`closest('tr')` 这类 DOM 标签名的误匹配。
5. 有条件的话，用 `python -m http.server` 跑起来，在真实浏览器里过一遍主要交互路径。

## Windows 用户注意

Windows 终端默认代码页不是 UTF-8，运行涉及中文输出的 Python 脚本时用 `python -X utf8 script.py` 避免乱码，这不影响脚本本身的正确性，只是终端显示问题。
