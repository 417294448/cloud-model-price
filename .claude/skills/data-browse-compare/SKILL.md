# 从 JSON 数据构建浏览 + 对比页面

## 这个 skill 解决什么问题

用户手上有一份 JSON（或可转成 JSON 的数据），里面是几十到几千条"同类实体"的记录——每条记录字段结构大致相同，但字段覆盖率参差不齐（不是所有记录都有所有字段）。用户想要一个页面：能浏览全部记录（搜索、筛选、排序），能勾选几条记录并排对比它们的差异。

典型场景：云服务定价表、商品/SKU 清单、API 模型规格、招聘岗位列表、竞品功能矩阵——任何"N 条记录 × M 个字段，字段有缺失，用户想挑几条细看差异"的数据。

## 核心方案：零依赖单文件静态页面

除非用户明确要求用某个框架，默认用**纯 HTML + 原生 JS + 内联 CSS**，理由：
- 数据是静态的，不需要后端
- 单文件双击即可打开，用户零门槛使用、分享
- 避免引入构建工具链的复杂度，对几千条记录的规模完全够用（渲染、排序、筛选都在客户端瞬间完成）

如果用户主动提到想用 React/Vue 或需要更复杂的交互，才转向对应技术栈；不要主动建议升级架构。

## 工作流程

### 第一步：分析数据结构（不要跳过，这决定了页面怎么设计）

在写任何页面代码之前，先看数据长什么样。用 `scripts/analyze_json.py` 快速摸底：

```bash
python scripts/analyze_json.py <path-to-json>
```

它会输出：条目总数、每个字段的覆盖率、字段值类型分布、数值字段的范围、布尔字段的 True 占比、数组/对象类字段的示例。

看这份报告时，带着这几个问题去读：
- **哪些字段几乎每条记录都有？**（覆盖率 >80%）→ 这些是浏览表格的核心列
- **哪些字段覆盖率很低（<20%）？**→ 不适合做浏览表的常驻列，但可能在对比视图里有价值，或者压根是元数据该忽略
- **数值字段的量级大不大？**→ 决定要不要做单位换算（比如美元/token 太小需要换算成美元/百万token）、格式化（大数字缩写成 12.5K/3.2M）
- **布尔字段多不多？**→ 如果有一批 `is_xxx`/`supports_xxx`/`has_xxx` 这样的字段，它们是"能力矩阵"的候选，适合做成标签墙或筛选开关
- **有没有数组/对象类型的嵌套字段？**→ 这些需要特殊渲染逻辑（join 成文字、拆成子行、或者用图标表示），不能直接塞进表格单元格
- **key 的命名有没有规律？**→ 如果同一个实体有多个 key 变体（比如同一模型不同区域/渠道各一条记录），想清楚是要合并展示还是保留独立条目——通常保留独立更简单也更诚实（不臆测哪些该合并）

如果分析后对"哪些字段该展示、能力矩阵怎么定义、要不要做单位换算"这类设计判断没有把握，用 AskUserQuestion 或者直接列出几个选项跟用户确认，而不是自己假设一个方案埋头写——这类页面的"什么该强调、什么该省略"高度依赖业务语境，用户一句话能帮你避免返工。

### 第二步：设计浏览表格

浏览表格是默认视图，展示全部记录，用户从这里挑出要对比的对象。

**必备交互：**
- 顶部搜索框（模糊匹配名称等关键字段）
- 按主要分类字段筛选（下拉选择，选项按出现频次排序更好用）
- 表头点击排序（数值列按数值排，文本列按字母排，**缺失值永远排最后**而不是排最前——排最前会让用户以为这是"最小值"）
- 分页（超过 100~200 条时必须分页，一次性渲染几千个 DOM 节点会卡顿；不要用虚拟滚动这种复杂方案，简单分页足够且更稳）
- 每行一个勾选框，用于选中要对比的记录

**能力矩阵字段的处理**：如果数据里有大量布尔能力字段（比如 20+ 个 `supports_*`），不要在浏览表格里把它们全部列成图标——太挤太吵。做法：
1. 浏览表格只挑 3~6 个**覆盖率高、用户最可能关心**的能力做图标列（比如"是否支持视觉"这种高频能力），或者干脆改用更结构化的字段（如果数据里有 `modalities: ["text","image"]` 这种数组字段，用它比用一堆布尔值更清晰）
2. 完整的能力矩阵放到对比视图里展开，而且只展示每个对象**自己命中**的能力（见下一节的"负结果不展示"原则）

**格式化细节：**
- 价格类数值：确认原始单位（很多定价数据是"每 token 美元"这种极小单位），换算成人类好读的单位（每百万 token 美元），千万不要直接把 `0.0000025` 糊给用户看
- 大数字（token 数、字节数等）：格式化成 `128K`、`1.5M` 这类缩写
- 布尔值：视觉上要一眼区分开／关，不要用纯文字 true/false

### 第三步：设计对比视图

对比视图不是"表格转置"这么简单，好的对比视图应该：

**布局：并排卡片优于长表格转置**——如果对比数量有上限（比如最多 3~4 个），用并排卡片（每个对象一张卡片，卡片内部按维度分区块）比横向滚动的表格更干净，尤其是字段数量多的时候。表格转置在对比对象超过 3 个或字段很多时会变得又长又难扫视。

**只比较、不列举全集**——这是最容易被忽略但影响体验最大的原则：
- 如果某个指标在**所有已选对象中都是空值**，直接不渲染这一行/这个区块，而不是让每张卡片都显示一个"—"。空对空的比较没有信息量，只会增加噪音。
- 对于"能力/标签"这类字段，每张卡片**只展示这个对象自己命中的**，不要展示"其他对象有但这个没有"的灰色占位——用户想看的是"它支持什么"，不是"它缺什么"（除非用户明确要求突出缺失项）。

**高亮最优值，但只在真正需要比较时才高亮**——数值类维度（价格、容量等）可以给"最优"的那个打标（更低价格/更大容量），但前提是：
- 只选了 1 个对象时不需要任何"最优"标记（没有比较对象，谈何最优）
- 明确"越低越好"还是"越高越好"，不要凭字段名瞎猜（价格显然越低越好，但"最大上下文"显然越大越好）
- 高亮手法克制一点：一个强调色 + 一个小标签就够了，不要同时叠加背景色+边框+粗体+变色四五种视觉手段，反而会互相打架看不清重点

**核心信息优先级更高的视觉权重**——如果数据里有一个"这就是用户最关心的那个数字"（价格、评分、核心参数），给它更大字号/更突出的位置，其余维度按重要性分组、用小标题分隔，不要把所有字段用同样的视觉权重平铺。

### 第四步：写入口交互（勾选 → 对比）

从"浏览"到"对比"的路径要顺畅，别让用户选完之后还要自己找入口：
- 勾选达到上限（如果有）时，可以自动跳转到对比视图（配合一个短暂的 toast 提示，别用浏览器原生 `alert()` ——样式无法定制、会阻塞界面）
- 勾选 1 个以上但还没到上限时，提供一个不遮挡内容的常驻入口（比如底部悬浮条），让用户随时能跳转，而不强迫立刻决定
- 提供"清空所有勾选"的按钮，并且如果有"对比"标签页/弹窗，也要有一个明显的关闭按钮——点击后清空选中并返回浏览视图，别让用户被卡在对比视图里出不去
- 所有计数显示（顶部徽标、悬浮条、对比视图内的计数）必须用同一个函数统一刷新，否则容易出现某处更新了、另一处没跟着变的不一致

### 第五步：把数据内嵌进最终交付的那一个文件

浏览器的 `file://` 协议禁止用 `fetch()` 读取本地文件，所以如果页面运行时依赖 `fetch('source-data/xxx.json')`，用户直接双击打开会加载失败，必须额外起一个 http server 才能用。**默认目标是让用户拿到的就是一个能双击打开的文件**，所以不要把"能双击打开的版本"和"日常编辑的版本"拆成 `index.html` + `dist/index.html` 两份——两份文件必然会不同步（改了源数据、改了页面逻辑，两边都要重新生成，很容易漏掉一边），交付一个自包含文件更简单也更不容易出错。

做法：让 `index.html` 本身就内嵌数据，用 `scripts/build.py` **原地更新**它（不指定 `--out`，默认输出路径等于模板路径）：

```bash
python scripts/build.py
# 等价于 python scripts/build.py --template index.html --out index.html
```

这个脚本是幂等的：如果 `index.html` 里已经有内嵌数据块，会整体替换掉旧的，不会重复插入、也不会让文件越滚越大。之后只要 `source-data/` 里的原始数据变了，重新跑一次这条命令刷新即可，`index.html` 永远是唯一、完整、可直接分发的产物。

页面里的加载逻辑仍然要写成"优先读内嵌数据、没有则退回 fetch"，这样开发阶段可以先不内嵌、直接用 `python -m http.server` 边改数据边看效果，效率更高；等要交付/分享的时候再跑一次 `build.py` 把最新数据焊进去：

```js
async function loadData() {
  let data;
  const embedded = document.getElementById('model-data');
  if (embedded) {
    data = JSON.parse(embedded.textContent);   // 交付版本：数据已内嵌，双击可用
  } else {
    const resp = await fetch('source-data/xxx.json');  // 开发阶段：需要 http server
    data = await resp.json();
  }
  ...
}
```

只有当用户明确要求保留"引用外部 JSON、通过 http server 访问"这种部署方式（比如要接入 CI、要托管在需要频繁更新数据但不想重新构建 HTML 的场景）时，才用 `--template`/`--out` 分开传参产出独立的 `dist/index.html`，并在这种情况下才需要保留 README 里"两种使用方式"的说明。默认情况下不要主动引入 `dist/` 目录或额外构建产物。

数据量较大（几 MB）时内嵌后文件会变大（JSON 展开通常比原文件本身还要大一些），这是预期的正常现象，跟用户说明一下就行，不必因此改用别的方案。

## 常见坑（都是踩过的，别重蹈覆辙）

- **`<td>` 不要直接设 `display: flex`**——一旦这样做，这个单元格就脱离了表格的 `vertical-align` 对齐规则，会和同一行其他列对不齐。要在 `<td>` 内部再包一层 `inline-flex` 的容器，`<td>` 本身保持 `table-cell`，并给 `th, td` 统一设 `vertical-align: middle`。
- **emoji 图标显示异常/变成方块**——某些 emoji（如 🖼、🖥、🗂、🎛）默认是"文本呈现"字符，不加变体选择符 `️` 在部分字体下会显示成单色小符号甚至方块。凡是用 emoji 做图标，都在后面加上 `️` 保险。
- **固定定位的悬浮元素会遮挡页面底部的其他控件**——比如悬浮对比条用 `position: fixed; bottom: 0`，如果页面本身在底部也有分页按钮之类的控件，滚动到底部时两者会重叠。用 JS 动态给被遮挡的容器加 `padding-bottom`，悬浮条出现时留出空间、消失时收回。
- **不要用 `alert()`/`confirm()` 做提示**——样式不可控、会阻塞页面。用一个简单的 toast（定时消失的浮层提示）代替。
- **排序时缺失值不要排在最前**——`null`/`undefined` 应该在升序和降序时都排到最后，否则用户会以为缺失值是"最小的"。
- **内嵌数据到 `<script>` 标签时转义 `</`**——如果原始 JSON 字符串里恰好包含 `</script>` 这样的子串（虽然罕见，但可能发生在带 HTML 内容的字段里），会提前截断标签。用 `.replace('</', '<\\/')` 处理。
- **原地更新内嵌数据的脚本要写成幂等的**——如果构建脚本每次都无脑往 `</head>` 前插入一份新的数据块，重复跑几次就会在文件里堆出好几份数据（`scripts/build.py` 用正则匹配已有的同 id 数据块并整体替换，就是为了避免这个问题）。写类似脚本时记得处理"文件里已经有一份了"的情况。

## 验证方式

写完页面后，不要只靠肉眼看一眼就说完成了，跑一遍这些检查：

1. **数据完整性**：用 Python 读一遍原始 JSON，统计条目数、随便抽几条记录的关键字段值，跟页面里搜索/筛选出来的结果做数值比对（比如"provider=X 的条目数"两边应该一致）。
2. **内嵌结果验证**：`build.py` 跑完后，检查 `index.html` 里的数据块能被 `JSON.parse` 正常解析、条目数对得上、内嵌脚本的 JS 语法没问题（用 Node 的 `new Function(jsCode)` 可以快速验证语法而不用真的跑浏览器）；如果是原地更新，同时确认文件里只有一份数据块（没有因为重复运行而残留旧数据或插入两次）。
3. **交互逻辑验证**：如果环境里没有真实浏览器可用，可以写一个轻量的 Node.js 脚本，用最简单的 DOM 元素桩（mock `document.getElementById` 返回一个带 `classList`/`addEventListener`/`innerHTML` 的假对象）加载页面里的 JS，模拟勾选、点击等事件，断言状态变化和渲染结果是否符合预期。这比反复口头确认"应该没问题"要可靠得多，尤其是对涉及好几个状态联动（勾选计数、悬浮条、对比视图）的功能。
4. 有条件的话，用 `python -m http.server` 跑起来，在真实浏览器里过一遍主要交互路径。

## Windows 用户注意

Windows 终端默认代码页不是 UTF-8，运行涉及中文输出的 Python 脚本时用 `python -X utf8 script.py` 避免乱码，这不影响脚本本身的正确性，只是终端显示问题。
